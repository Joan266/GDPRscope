### Agentic RAG — lo que hace db/rag.py hoy

```
1. CORPUS INDEX    — data/corpus_index.json inyectado en system prompt
2. INTENT          — extract_intent() → QueryIntent dataclass
                     {controller_name, authority, jurisdiction, gdpr_articles,
                      year_min, year_max, sort_by, has_fine}
                     CONSERVADOR: solo sort_by se aplica a SQL; el resto NO filtra
                     (demasiados falsos negativos con exact-match)
3. CONTROLLER PRE-FILTER — _find_controller_docs() ILIKE en controller_name
                           Solo docs con embedded child chunks (JOIN + IS NOT NULL)
4. HYBRID SEARCH   — tsvector (BM25) + C-SPANN vector + RRF fusion
5. PARENT CONTEXT  — fetch child chunks → expande a parent para contexto LLM
6. RERANK          — rerank_by_metadata() por fine_amount o decision_year
7. MEMORY          — user_memory table: inject past session context
8. ITERATIVE       — _evaluate_sufficiency() → si insuficiente, segunda pasada
                     con query refinada, sin doc_ids filter
                     Merge: (contexts + new_ctx)[:top_n + 4]
```

## Diagnóstico raíz de los problemas

### 1. Faithfulness = 35% — el problema más crítico

El LLM inventa detalles cuando el doc relevante no está en el contexto recuperado.
Con HR@5=36%, el 64% de las veces el doc relevante no está en el top-5 → el LLM
responde desde conocimiento paramétrico (alucinaciones).

**Causa A:** Retrieval pobre → no encuentra el doc correcto → LLM improvisa.
**Causa B:** Prompt no instruye explícitamente al LLM que DEBE limitarse al contexto.
            El prompt actual dice "use the context" pero no dice "if context is
            insufficient, say so explicitly instead of generating an answer."

Impacto de las causas:
- Causa A contribuye ~60% del problema (necesita más datos + mejor retrieval)
- Causa B contribuye ~40% (fix rápido, alto impacto inmediato)

### 2. HR@5 = 36% — retrieval insuficiente

- 993 docs es poco corpus. GDPRhub tiene 4.500+ decisiones disponibles.
- `article_lookup` falla porque exact-match SQL en gdpr_articles[] no tolera variantes
  ("Article 32" vs "Article 32 GDPR" vs "Art. 32")
- `compliance_advice` y `threshold_comparison` son preguntas de síntesis que
  requieren múltiples docs — el golden set los trata como single-doc retrieval (bug del eval).
- Intent extraction conservador (solo sort_by) no filtra por artículo/año en SQL.

### 3. Latencia ~70s — inaceptable para producción

- e5-large-v2 en CPU: lento. Necesita GPU o batching.
- Cada query hace 4 llamadas LLM: intent + sufficiency check + generate + judge (eval)
- Sin streaming: usuario espera 70s sin feedback visual.

### PRIORIDAD 3 — HyDE para article_lookup [45 min, impacto medio]

HyDE (Hypothetical Document Embeddings): en vez de embeber la query directamente,
pedir al LLM que genere un párrafo hipotético que respondería la pregunta,
y embeber ESE párrafo. Mucho mejor para preguntas de tipo "qué dice el artículo X".

**Dónde:** `db/rag.py` → nueva función `hyde_embed()`, llamada desde `query()` cuando
`intent.gdpr_articles` no está vacío.

```python
def hyde_embed(bedrock_client, query_text: str, intent: QueryIntent) -> list[float]:
    """Genera embedding HyDE: LLM → párrafo hipotético → embed."""
    ac = _get_anthropic_client()
    articles = ", ".join(intent.gdpr_articles[:3]) if intent.gdpr_articles else "GDPR"
    hyde_prompt = f"""Write a brief excerpt from a GDPR enforcement decision that would
answer this question: {query_text}

Focus on {articles}. Write 2-3 sentences as if from an actual DPA decision.
Do not add commentary, just the excerpt."""

    msg = ac.messages.create(
        model=MODEL_ID_LLM,
        max_tokens=150,
        messages=[{"role": "user", "content": hyde_prompt}],
    )
    hypothetical_doc = "passage: " + msg.content[0].text.strip()
    return embed_query(bedrock_client, hypothetical_doc)

```

**Impacto esperado:** article_lookup HR@5 20% → 40-50%

### PRIORIDAD 4 — Normalizar gdpr_articles en DB [30 min, impacto medio]

El exact-match SQL `AND %s::TEXT = ANY(d.gdpr_articles)` falla porque los artículos
están almacenados con variantes: "Article 32", "Article 32 GDPR", "Art. 32", etc.

**Fix:** normalizar en ingest.py antes de insertar, Y actualizar los existentes:

```python
# En db/ingest.py, función que procesa artículos:
def normalize_article(art: str) -> str:
    """Normaliza a 'Article X GDPR' o 'Article X(Y) GDPR'."""
    import re
    art = art.strip()
    # Quitar "GDPR" trailing si ya está
    art = re.sub(r'\s+GDPR$', '', art, flags=re.IGNORECASE)
    # Normalizar "Art." → "Article"
    art = re.sub(r'^Art\.?\s+', 'Article ', art, flags=re.IGNORECASE)
    return f"{art} GDPR"

# SQL para normalizar existentes (ejecutar una vez):
# UPDATE documents SET gdpr_articles = array(
#   SELECT normalize_article(a) FROM unnest(gdpr_articles) AS a
# ) WHERE ...
# (CockroachDB no tiene UDFs fácilmente — hacerlo en Python con UPDATE batch)
```

**Alternativa más simple:** cambiar el filtro SQL de exact-match a ILIKE:
```sql
-- En _build_filter_clause():
-- En vez de: AND %s::TEXT = ANY(d.gdpr_articles)
-- Usar: AND EXISTS (
--   SELECT 1 FROM unnest(d.gdpr_articles) AS a WHERE a ILIKE %s
-- )
-- Con valor: f"%{article_short}%"  (e.g., "Article 32" sin " GDPR")
```

**Impacto esperado:** article_lookup HR@5 mejora si se combina con HyDE.

### PRIORIDAD 5 — Streaming response en UI [1h, impacto UX]

Sin streaming, el usuario espera 70s con spinner. Con streaming, ve texto aparecer
en ~2s → experiencia radicalmente mejor aunque el tiempo total sea el mismo.

**Dónde:** `db/rag.py` + `ui/catalog.py`

En `rag.py`, crear variante streaming de `call_llm()`:
```python
def call_llm_stream(ac_client, system_prompt: str, user_prompt: str):
    """Yields text chunks via Anthropic streaming API."""
    with ac_client.messages.stream(
        model=MODEL_ID_LLM,
        max_tokens=MAX_TOKENS,
        system=system_prompt,
        messages=[{"role": "user", "content": user_prompt}],
    ) as stream:
        for text in stream.text_stream:
            yield text
```

En `ui/catalog.py`, usar `st.write_stream()` con un generador:
```python
# En el Research tab:
with st.chat_message("assistant"):
    response_placeholder = st.empty()
    full_response = ""
    for chunk in rag_module.call_llm_stream(ac, system_p, user_p):
        full_response += chunk
        response_placeholder.markdown(full_response + "▌")
    response_placeholder.markdown(full_response)
```

**Impacto esperado:** Perceived latency: 70s → ~2s first token

## Riesgos y notas importantes

### CockroachDB limits (serverless)
- `BATCH_SIZE=10` en ingest — no subir, causa lock budget exceeded
- `autocommit=True` en TODAS las conexiones psycopg3
- Si embed.py falla a mitad: es idempotente, relanzar sin miedo

### Anthropic API créditos
- Cada eval completo (~35 min, 25 preguntas) gasta aproximadamente $0.50-$1.00
- Eval solo-retrieval (sin --llm) es GRATIS — úsalo para iterar rápido
- La intent extraction en eval (extract_intent) también gasta créditos si hay ANTHROPIC_API_KEY

### Encoding Windows
- SIEMPRE usar `PYTHONUTF8=1` antes de cualquier script Python
- Si ves UnicodeDecodeError: añadir `encoding='utf-8'` en los `open()` afectados
