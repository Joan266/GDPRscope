### Patron: 3 tipos de fallo

1. **Multi-doc** (gs-002, gs-018, gs-019, gs-020, gs-025): necesitan 2-3 docs de distintas fuentes. RRF favorece concentracion en 1 doc.
2. **Situacion→precedente** (gs-023, gs-028, gs-029): describen un escenario y esperan encontrar un caso real similar. La distancia semantica entre "hospital ransomware" y "Dutch DPA fined hospital for Article 32" es demasiado grande para vector search.
3. **Abstracto sin entidad** (gs-013, gs-015, gs-016, gs-021): queries de tema sin nombre de empresa ni caso. Solo dependen de vector similarity.

### Prioridad 2: Mejorar categorias debiles

Ideas ordenadas por impacto/esfuerzo:

1. **Query expansion para scenario/conceptual** — Reformular la query en 2-3 variantes (LLM) y hacer union de resultados. Ejemplo: "hospital ransomware" → "DPA fine hospital Article 32 security breach" + "healthcare data breach inadequate measures". Coste: 1 llamada Haiku extra por query.

2. **Multi-doc diversity en RRF** — Actualmente si un doc tiene 5 chunks en top-20, ocupa 5 de 8 slots. Penalizar docs ya representados para forzar diversidad. Facil de implementar en `fetch_parent_context`.

3. **Jurisdiction filter para cross_jurisdiction** — Cuando la query menciona "different European DPAs" o "cross-jurisdiction", forzar resultados de al menos 2 paises distintos.

4. **Scenario→article inference** — En `extract_intent`, inferir articulos GDPR del escenario descrito. "ransomware hospital" → Articles 32, 33. Esto activaria HyDE con articulos correctos.

### Prioridad 3: UI y demo

- Revisar que el catalog funcione con 8K docs
- Demo flow: query → citations → streaming response
